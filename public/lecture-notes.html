1. What you will learn

By the end of this workshop, you should be able to:

  • Read a short Python program and predict a change before running it.
  • Choose where setup, drawing and repeated logic belong.
  • Use variables, expressions, conditions and indentation to control behaviour.
  • Change and combine statements to create your own behaviour.
  • Observe values, read an error and make a reasoned correction.
Your decisions matter. A shortcut supplies text such as if …:. You still decide the condition, the values, the body and where it belongs. You can type, delete or rewrite any line.

2. Using the workspace

  1. Click a position in game.py.
  2. Choose a syntax shortcut. Edit its preview if useful.
  3. Click Insert at cursor. The inserted text is selected: type to replace it, or use an arrow key to keep it and move the cursor.
  4. Check names and indentation. A shortcut does not automatically create missing variables or actors.
  5. Click Run Python. Observe the larger preview, variables and output.
  6. Use Pause and Step update to advance one update at a time. Click the game canvas when you want keyboard control.
  7. Use Stop & edit to return to your source. Run again to start from setup.

Enter automatically indents Python blocks. Tab moves focus between controls; use four spaces when manually indenting. Ctrl+Z (Command+Z on Mac) undoes edits, including snippet insertion and loading Starter. The toolbox groups syntax into Setup, Draw, Logic, Structure and Debug. Its editable preview stays beside your program in the desktop layout. Both editors use matching colours for keywords, names, functions, strings, numbers and comments. Your latest source is saved in this browser when storage is available; download a copy before leaving a shared computer.

3. Three parts of a program

WIDTH = 800
HEIGHT = 600
player = Actor("spaceship", (150, 300))

def draw():
    screen.clear()
    player.draw()

def update():
    if keyboard.right:
        player.x += 5
PartWhen it runsYour decision
Setup: statements outside functionsOnce when the program startsWhat objects and initial values do I need?
draw()When the screen is redrawnWhat should be visible?
update()Repeatedly during the gameWhat should be checked or changed each time?

def defines a function. Its indented body runs when the function is called. Pygame Zero calls draw() and update() for you. You must call other functions you define when you want their bodies to run.

Predict: What happens if player.x = 150 is placed at the start of update()? Why might the player appear unable to travel?

4. Coordinates, variables and expressions

The top-left of the screen is (0, 0). Increasing x moves right. Increasing y moves down. In our examples, an actor's position is its centre.

speed = 5              # Store a value
player.x = 150         # Assign a new position
player.x += speed      # Read x, add speed, store the result
player.y -= 3          # Move upwards

A variable has a name and a current value. An expression computes a value: speed * 2, WIDTH - 30 or score + 1. player.x is an attribute of the actor named player.

Trace by hand: Starting at x = 150, what is x after three updates with Right held and speed = 5? Write all three intermediate values before running.

player.x += 5 inside update() means five pixels per update while the condition is true. It does not mean five pixels per physical key press. For a later extension, def update(dt): receives elapsed seconds; player.x += 120 * dt represents a speed of 120 pixels per second.

5. Conditions and indentation

if keyboard.right and player.x < WIDTH - 30:
    player.x += 5

The condition evaluates to True or False. The body runs only when it is true. The colon starts the block; indentation shows which statements belong to it.

OperatorMeaning
=Assignment: store a value
==, !=Equal to; not equal to
<, >, <=, >=Compare values
and, or, notCombine or reverse Boolean conditions
if score >= 10:
    message = "Target reached"
else:
    message = "Keep going"

An if / else selects one branch. Two separate if statements are two independent checks. If both are true, both bodies run.

Discuss: If Left and Right are both held, what will two separate movement conditions do? Would using elif change the result?

6. State, repetition and order

State is the information your program currently remembers: position, score, speed, or whether something has already happened. Your program changes that state over time.

score = 0

def update():
    global score
    if player.colliderect(coin):
        score += 1

This fragment requires player and coin to have been created in setup. global score allows the function to reassign the module-level variable. Changing player.x changes an object attribute and does not require global player.

Debugging question: Why does the score rise repeatedly while the actors overlap? The condition is checked on each update. How could you make the event count once?

Possible designs include moving the coin elsewhere, remembering that it has been collected, or detecting the transition from “not touching” to “touching”. Choose the design that fits your game. Each requires different state or actions.

for i in range(3):
    print(i)

This prints 0, 1 and 2 in one execution of the loop. If placed inside update(), all three iterations happen on each update. A Python loop is not a delay between animation frames.

Statements execute in order. Assigning player.x = 100 before adding 5 gives a different result from assigning it after adding 5. Reordering code is a programming decision.

7. A workflow you can repeat

  1. Describe: Write one sentence about the behaviour you want.
  2. Predict: State what one variable should do.
  3. Edit: Make a small code change. Use a shortcut for repetitive syntax.
  4. Run: Try the condition that should trigger the behaviour.
  5. Inspect: Compare the output with your prediction. Pause, step, or use print().
  6. Fix: Explain a likely cause, change one thing, and run again.
ProblemWhat to inspect
SyntaxErrorThe reported line and nearby punctuation: colon, brackets, quotes
IndentationErrorWhich statements should be inside the function or condition?
NameErrorSpelling, capitalisation and whether the name was defined before use
No error, wrong resultCondition, sign, execution order, repeated updates and initial values

The error output may include adapter internals. Look for game.py, its line number and the final error message. Stop terminates the browser worker, including an accidental endless loop. Step update advances an entire update and redraw; it is not a line-by-line debugger.

8. Practice: make decisions in code

A. Change and explain

Load Starter. Predict the effect of changing 5 to 2, then to −5. Run each version. Explain the difference between the amount of movement and its direction.

Evidence: three predictions and one sentence comparing them with observations.

B. Add a behaviour

Add Left movement yourself. Then choose a second key and give it a different action. Insert a shortcut if helpful, but edit the names and values.

Evidence: identify the condition and body of each rule; explain where you placed them.

C. Keep an actor on screen

Add a boundary condition. Try starting near the edge and moving by a large amount. Does checking the position before moving guarantee the next position stays inside? Improve your rule using the proposed next position or a clamp such as min().

Evidence: one failing example and your revised code.

D. Design your own rule

Choose a behaviour: score after crossing a line, teleport at an edge, move automatically until a condition changes, or collect an object once. Write the rule in English, list the state you need, then implement it.

Evidence: explain your condition, state change and why it happens at the right time. Collision is optional.

E. Find a logical bug

Use the repeated-score fragment in section 6. Create the two actors and draw them. Make them overlap. Observe score while paused and stepping. Implement one method to count the event once.

Evidence: explain why your first version repeated and how your revision changes the state.

9. A small worked solution

Read this after attempting task B. This complete program supports both directions and keeps the actor's centre within a margin. The choices are visible in the code.

WIDTH = 800
HEIGHT = 600
speed = 5
player = Actor("spaceship", (150, 300))

def draw():
    screen.clear()
    player.draw()

def update():
    if keyboard.right:
        player.x = min(WIDTH - 30, player.x + speed)
    if keyboard.left:
        player.x = max(30, player.x - speed)

Extend: Replace the fixed distance with time-based movement. Explain your units: pixels per update or pixels per second.

10. What this preview supports

This prototype executes Python using Pyodide. A small display adapter supplies selected Pygame Zero names; it does not run the complete Pygame Zero package. Regular Python conditions, loops, functions, arithmetic and standard-library random work.

  • Actor(image, (x, y)): built-in images are spaceship, alien, coin and ball. Supported attributes include x, y, pos, angle and edges. Actors use 52 × 52 bounding boxes in this preview.
  • actor.draw(), rectangular colliderect(), keyboard.right and other keyboard names.
  • screen.clear(), screen.fill("navy"), and screen.draw.text(text, (x, y), color="white", fontsize=24).
  • draw(), update() or update(dt), plus print() output.

The adapter targets 60 updates per second and supplies a fixed dt of 1/60. Browser scheduling may run slower; it is not a timing benchmark. Mouse event hooks, sound, clock scheduling, animation helpers, custom images and the complete screen drawing API are not implemented. Unsupported features should be run in desktop Pygame Zero. A downloaded .py file contains your code; desktop use also needs the matching image files in an images/ folder and Pygame Zero installed. The browser's built-in illustrations are not bundled in that download.

First run downloads the Python runtime from a CDN and needs internet access. Your source is passed to the browser worker for execution. Each Run starts a fresh program; Stop preserves your source and the last displayed state.

11. Teacher guide and checkpoints

LessonSuggested sequence
1 · Structure and decisions5 min: prediction; 10 min: setup/draw/update; 10 min: edit and trace values; 15 min: tasks A–B; 5 min: explain a condition and body.
2 · State and debugging5 min: recap; 10 min: repetition and state; 15 min: tasks C or E; 10 min: personal rule D; 5 min: explain a bug and fix.

Assess explanations and code changes. Ask students to point to the statement that stores a value, the condition that permits an action, and the indentation that defines its body. A finished game alone is insufficient evidence of understanding.

Useful prompts: “What happens on the next update?” “Which value changed?” “What would happen if those two lines swapped?” “Which part of this snippet did you decide?”

Teacher answer cues
  • Three rightward updates from 150 at speed 5 produce 155, 160 and 165.
  • Resetting x on every update prevents accumulated movement.
  • Opposing independent movements can cancel; elif gives priority to the first true branch.
  • A coin that remains touching can score on every update. Respawning or recording collection changes subsequent behaviour.
  • A pre-movement boundary check can overshoot. Check the proposed value or clamp the final position.

Exit ticket

  1. Explain one difference between draw and update.
  2. Show a condition and explain when it is false.
  3. Describe one prediction, observation and correction from your own work.
  4. Identify one decision you made that a snippet did not make for you.
